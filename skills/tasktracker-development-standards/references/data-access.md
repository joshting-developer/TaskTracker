# API 資料存取架構檢查

新增或修改HTTP API、Repository、資料查詢、前端資料載入或輪詢時，必須執行資料存取審查。

1. 明確列出呼叫端需要的資料欄位與範圍。
2. 列表查詢必須有明確的資料上限與穩定排序。
3. 篩選與分頁優先在SQL層執行。
4. 不得以載入整個Workspace作為一般頁面或單一Project的預設資料取得方式。
5. 詳細資料、歷史、留言及工時應按需讀取。
6. 評估呼叫頻率、SQL RTT、查詢次數及Response Size隨資料量成長的情況。
7. 相關測試必須驗證資料讀取範圍，不能只驗證SQL次數與既有回應相同。
8. 發現尚未處理的P1問題，必須明確列為未完成或受阻，不得宣稱整體效能驗收通過。

效能量測使用專案內performance-optimization與benchmark，按[配置](../../../docs/performance-skills.md)搭配；不能以本機SQLite結果取代遠端MySQL或實際部署拓樸驗證。

## 審查時需交代的內容

- 呼叫端／操作：頁面、角色的有效permission與scope、觸發時機、預期欄位及資料期間；列表、詳細與活動分開。
- SQL：where範圍、排序tie-breaker、上限與分頁、COUNT／深OFFSET／搜尋的成長、預載關聯及授權快照讀取。回應分頁但先載全租戶到PHP仍不符合。
- 頻率：首次載入、路由切換、mutation後、WebSocket事件、斷線備援、隱藏分頁與多分頁；single-flight不等於已移除全量輪詢。
- 成本：讀取／掃描列數、查詢次數與SQL RTT、寫入量、原始／壓縮bytes、HTTP時間分開記錄；有界筆數不等於固定bytes或固定延遲。Resource不得lazy load。
- 驗證：增加無關Project／活動資料後，檢查SQL條件及實際結果範圍、回應欄位／大小、權限與撤權。以同環境、同範圍比較，不能把不同DTO的單次觀察當p95或加速倍率。
- API改版：列呼叫端移轉與舊入口退役條件，前後端／工具／測試／文件同步；安全、資料與revision／requestId語意保留。

新增端點不代表前端已切換。相關頁面必須以實際Network請求驗證不再走過量入口，才可結案該端到端改善。DI改造不得用更多初始化、查詢或更大payload換取表面分層；DI與效能待辦分別驗收。
