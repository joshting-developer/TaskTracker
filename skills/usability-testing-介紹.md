## 上游內容與實際能力

原文涵蓋定義任務、選主持或非主持式測試、找參與者、試跑、主持與觀察、歸納發現及重測。任務腳本要求描述使用者目標, 不洩漏按鈕名稱或正確路徑；主持時不急著提示、不替設計辯護, 記錄猶豫、回頭與理解差異。

它的強項是**研究程序、任務題目與報告格式**。它沒有自帶真人、錄影服務、瀏覽器自動化或分析平台；需要已有的試用環境及實際觀察資料。缺資料時, 上游要求明確標示缺口, 不捏造數字補滿報告。

上游 README 同時寫明：OpenAddict 的測試配置已設好, 尚未實際執行。因此不能用它的產品宣傳或可安裝狀態, 推論 skill 已有實證效果。

## 怎麼用在我們的產品

| 不適合拿來驗證找得到入口的題目 | 比較適合的任務題目 |
| --- | --- |
| 點首頁「更多」把待辦轉卡 | 昨天記下的小事需要團隊追蹤了, 把它安排進 first 的正式工作 |
| 點「工時月曆」選今天登記 0.5 | 把今天處理某件工作的半小時記下來, 並確認紀錄在哪裡 |
| 開看板選泳道再切狀態 | 找出這個專案正在進行的工作, 把你剛做完的一件更新好 |

這些是本輪撰寫的題目建議, 不是已經跑過的測試。若參與者不認識 Epic／卡片等用語, 要用他熟悉的工作情境描述, 不先教產品詞彙。

## 需要留下哪些資料

每次任務記：獨立完成／提示後完成／未完成、實際路徑、第一個卡點、提示次數、錯誤與回復方式、參與者原話。時間只能記實際量到的時間, 並說明是否含思考出聲與主持人插話。

少量試用先看具體障礙與重複模式, 不把「兩個人有一個卡住」說成產品整體成功率只有 50%。也不要把參與者提出的解法直接當成已確認功能需求；先找他要解決的問題。

## 需要調整的地方

- 原文列主持式 5–8 人等樣本建議, 以及「5 人找到 85%」的常見說法；本專案不把它當任何產品都成立的保證。探索卡點與量化驗收需要不同研究設計。
- 原文建議排除員工／朋友；對內部團隊工具, 同事可能就是目標使用者。本專案建議先用**沒有參與設計或開發、但確實有專案協作需求的同事**試跑, 將便利樣本與熟悉度明列, 不聲稱代表所有 SaaS 客戶。
- 主持人不該為了滿足固定等待秒數讓參與者受挫。事先約定何時提示／結束, 把協助記下, 比盲守上游範例的時間更有用。
- AI 可以準備腳本、整理你提供的紀錄與協助比對問題；不能代替你實際觀察真人, 也不能自行假造引用、滿意度、成功率或 SUS 分數。

建議先用少量目標使用者做試跑, 每人 3–4 個任務, 修正測試題目與明顯卡點後再找下一批人。具體範圍與觀察表見 [TaskTracker 可用性驗證方案](../docs/可用性驗證方案-2026-11-04.md)。
