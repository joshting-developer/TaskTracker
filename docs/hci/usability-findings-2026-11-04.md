# TaskTracker 可用性 findings：任務流程與卡點

日期：2026-11-04（Asia/Taipei）。使用 [usability-testing](../../skills/vendor/usability-testing/SKILL.md) 整理任務、觀察、程度與報告, 搭配 [Cognitive Walkthrough 逐步結果](cognitive-walkthrough.md)。**這是 AI 輔助走查報告, 真人參與者為0。** 初次走查沒有修改 UI；使用者後續授權修正，結果見下方修正紀錄。

## 摘要

核心任務可經可見入口操作完成, 轉卡、看板狀態、工時、邀請及 Project 授權都有實際保存／畫面證據。較值得先改善的是：**草稿藏在另一個 tab 時讓操作消失, 以及重整後查閱範圍變掉。** 手機速記入口與閱讀／編輯分工也值得再測, 但沒有真人資料可以說使用者真的會迷路或不滿意。

本輪列出四項改善：兩項 Major（F03／F01）、一項 Minor（F02）、一項 Minor且以理解風險為主（F04）。沒有觀察到主任務的 Critical blocker。程度依本輪操作影響評估, 不沿用上游需要「多數使用者」才能成立的頻率描述；目前無法評估真人發生率。

## 方法

- 範圍：T1–T8, 詳 [事前計畫／可直接使用的真人腳本](usability-test-plan-2026-11-04.md)。用目標而非指定點擊路徑評估, 再以介面文字操作。
- 環境：`6d18057`, production build；獨立 preview 5175／Laravel 13024, SQLite 僅在測試容器 `/tmp`, 無使用者 volume。主服務／資料庫／seed 未變更。
- 角色脈絡：3個瀏覽器 context, 分別 owner、developer、新成員；新成員依階段獲 first reader／developer。context 不是三位真人參與者。
- 取證：45份畫面／狀態、2種尺寸, 人工檢視關鍵截圖；用 UI 走正常路徑, fixture API 僅用於補八筆交辦及核對資料。單次轉卡 request abort 是刻意注入的網路失敗, 未使用業務 mock。
- 工程限制：AI 已知道產品, 不能真的消除內部知識；瀏覽器自動定位成功不證明新手注意得到。曾用不正確的精確 accessible name 定位 Project 成員選單, 讀取實際語意後改正；兩次定位 timeout 不列產品缺陷。
- 不是本輪工作：完整回歸、全量 API 安全稽核、真人主持、錄影、招募、滿意度／SUS／完成率統計、所有載入／錯誤狀態。本輪建置成功, 沒有重跑整套 E2E 來代替可用性判斷。

## Critical findings

本輪未觀察到使主路徑完全無法完成的 Critical 問題。未測狀態與真人資料仍有缺口, 不代表產品沒有 blocker。

## Major findings

### F03 · 跨待辦 tab 時, 隱藏草稿讓其他操作消失

**實測：** owner 在「我交辦的」可見三個待辦操作入口。切回「我的待辦」編輯「準備會議摘要」並保留草稿, 再切「我交辦的」, 三個「更多」變0, 編輯輸入欄也不在當前 tab, 畫面未說明不能操作的原因。「顯示全部待辦」同時 disabled。回原 tab 取消草稿後, 三個入口恢復。

**影響與界線：** 要繼續處理其他交辦, 需知道被另一 tab 的草稿卡住；容易被誤認為權限或系統異常。草稿仍在, 沒有證據顯示資料遺失。只實測 owner 的此組資料, 不聲稱多數使用者都會遇到。

**對應判斷：** Q3動作意義與Q4回饋不足；未保存狀態不可見、復原路徑隱藏。來源是 [TodoHome.vue](../../frontend/src/components/TodoHome.vue) 第90行, 每筆操作都受整個元件的 `!draft` 控制；tab第77行切換未說明如何處理草稿。

**最小建議：** 切 tab 前允許「繼續編輯／保留草稿再切換／放棄」的清楚選擇, 或常駐顯示草稿所在項目與返回入口。若暫時禁止其他操作, 顯示原因, 不直接讓入口消失。先選一種一致模型, 不需要新增複雜草稿中心。

**驗收：** 同樣序列下, 使用者在另一 tab 能知道為何不可操作及如何恢復；原草稿不被默默丟棄。證據：T2-06／T2-07／T2-08。

### F01 · 功能頁保留了, 目前查閱的範圍卻沒有保留

**實測兩例：**

1. developer 的「我的任務」為4筆, 重整同一 Project URL後變「任務列表」6筆。
2. 工時設為2026-10＋全團隊, 重整 `/time` 後仍在工時頁, 但月份回2026-11、成員回developer。

**影響與界線：** 中斷後要重新判斷目前資料範圍, 可能誤把不同集合／月份的資訊當同一份。未觀察到因此做錯資料修改；資料本身沒有消失。前輪獨立功能路由修正有效, 此處是下一層的範圍保存缺口。

**對應判斷：** Q4未形成穩定工作上下文。[App.vue](../../frontend/src/App.vue) 第42行 scope 初始化 `all`, 第157行 URI未包含目前範圍；[TimeCalendar.vue](../../frontend/src/components/TimeCalendar.vue) 第8行初始化當月與本人。

**最小建議：** 將目前範圍／查閱條件保存在網址或可靠的 session state, 無效／無權限條件明確回退。這不是恢復「存為視圖」：只保存當下工作位置, 不新增命名、分享或管理視圖。

**驗收：** 上述兩例重整／分享後範圍清楚且一致；換人登入或權限改變時不錯用前一人的條件。證據：T1-02／T1-05／T5-06／T5-07。

## Minor findings

### F02 · 手機「快速記一件事」需要先越過專案區

**實測：** owner 的390×844首頁, 只有 first、second 與建立專案卡, 小待辦輸入欄 top y≈1095（頁面未捲動）。桌面兩區並列, 手機依序排列後, 第一屏沒有速記入口。

**影響與界線：** 有向下捲動的可行路徑, 所以不是 blocker；但「先快速記下」需要知道下方還有另一區。會不會因此放棄／找不到尚無真人資料。這是專案優先與速記並存的設計取捨, 不代表前輪專案入口修正無效。

**來源：** [App.vue](../../frontend/src/App.vue) 第455行首頁排列, [workspace.css](../../frontend/src/workspace.css) 第250行的單欄布局。超過兩個專案可能更靠下是布局推論, 本輪沒有測100專案。

**最小建議：** 首屏提供「記小事／我的待辦」直接入口或區域切換, 不再次用單純上下交換犧牲找專案。是否需要首頁分頁用真人 T1／T2 對照確認。

**驗收：** 同樣手機起點, 能直接到達速記, 並保留清楚專案入口；請目標使用者分別執行兩項任務, 記錄找錯位置／需要提示的情形。證據：T2-05。

### F04 · 為閱讀點標題, 先看到完整編輯表單

**實測：** developer 點列表標題打開可編輯側欄, 有標題、描述、專案、狀態、類型、優先級、負責人、日期、Epic、估時等欄位；要用完整閱讀頁, 再按「開啟完整頁」。reader 則直接進完整頁, 唯讀標示清楚。

**解釋：** 一個以閱讀要求為目的的使用者可能誤以為需要編輯或保存才能繼續；這個理解風險尚未由真人確認。快速編輯本來就有價值, 不把有表單本身當缺陷。

**最小建議：** 比較「標題預設閱讀＋顯式快速編輯」和目前做法, 或讓兩種動作有更明確標籤。建議屬於產品操作模式選擇, 未直接修改。

**來源：** [App.vue](../../frontend/src/App.vue) 第488行標題 `openIssue(issue)` 與另一個完整頁按鈕；第252行 `openIssue` 依可寫權限決定完整頁。證據：T1-03／T1-04／T7-04。

沒有為湊數再列色彩、icon或留白偏好。本輪聚焦工作流程, 沒有重跑完整視覺樣式稽核。

## 值得保留的行為

- 轉卡失敗後表單保留, 重試成功, 描述與責任資訊仍在；沒有「轉卡後失去承辦人」的證據。
- 看板逐卡狀態選單可以完成操作, 不必依賴拖曳；Default 明示只含目前專案。
- 工時日期帶入、整數分鐘錯誤與本人修改入口可理解, 保存後紀錄可找到。
- 通知能定位預覽外的舊待辦；速記未保存離開時有保護。
- 邀請後的空狀態解釋仍需 Project 授權；reader 顯示唯讀, 不會僅因加入 Workspace 看見所有專案。
