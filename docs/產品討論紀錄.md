# TaskTracker 產品討論紀錄

建立／最後更新：2026-10-19（Asia/Taipei）

這份文件持續整理我們的產品討論, 作為下一輪討論與實作的共同入口。使用者要求邊討論邊更新, 避免決策、問題與理由只留在聊天裡

## 如何維護

- 每輪有新的需求、選項、決策或修正, 同步更新對應章節與最後更新日期
- 使用者明確採納才標「已確認」；助理提出的方案標「建議／待確認」, 不把追問或沒有反對當成同意
- 「已實作」只描述目前原型行為, 不代表正式產品規則已定案
- 改變方向時記錄原方案、新方案與原因, 舊紀錄保留在討論沿革, 不讓兩份矛盾規格同時生效
- 功能細節連到專門設計文件, 本文件保留產品決策與理由；決策確認後再同步受影響的文件與實作
- 純產品討論先整理文件, 是否實作依當輪指示與既有授權判斷

## 已確認的主要操作流程

使用者確認：「workspace → 建立專案 → 專案可以開 issue」

```text
Workspace 工作空間
└─ Project 專案
   └─ Issue 工作項目
```

操作順序：進入工作空間 → 建立或選擇專案 → 在該專案新增 Issue, 並使用清單、看板與詳細內容管理工作

- 工作空間整理它所屬的專案, 可以包含多個專案
- 專案整理它所屬的 Issue, 可以包含多個 Issue
- 每個專案屬於一個工作空間, 每個 Issue 屬於一個專案
- 新增 Issue 時固定目前專案, 個人或團隊使用都沿用這個層級；個人功能範圍仍待確認
- 目前原型的 Task、Bug、Feature、Epic 都是 Issue 類型；Epic 與子任務的關係發生在專案內, 不增加專案上方的層級

已確認工作流程、資料層級及邀請須有權限。帳號如何建立／取得工作空間、能否加入多個空間、成員角色與具體邀請政策仍按下方待討論項目處理

## 已確認：邀請需要權限

使用者補充：「有權限的帳號或者說有權限的 Workspace 可以去邀請使用者加入」

已確認的要求是邀請入口與操作須有授權, 不是所有註冊帳號都能邀請他人進入任意 Workspace

建議將規則表達為：**帳號在指定 Workspace 具備「邀請成員」權限, 才能代表該 Workspace 邀請使用者加入**

- 帳號是操作的人, Workspace 是邀請所屬的空間, 邀請指向明確的 Workspace
- 建議以帳號在該空間的成員資格／角色判斷權限, A 空間的權限不延伸到 B 空間
- 建立邀請時由後端檢查授權, 隱藏前端按鈕只負責操作體驗
- 「可以邀請」與「可以給受邀者哪些角色」分開定義, 本輪尚未授權邀請者任意提升他人權限
- 目前原型僅 admin 可邀請, 是現有行為；正式要給 owner／admin 或自訂角色哪些權限仍待確認
- 如果「有權限的 Workspace」也包含空間方案／設定允許邀請的意思, 可再加空間層級開關；是否需要這一層還沒決定

這項確認沒有一併決定受邀者是否必須先註冊、個人空間額度、多空間切換或加入後的專案存取範圍, 這些保留在待討論清單

### 複雜度評估與第一版建議（待確認）

使用者問：「這樣會太麻煩嗎, 還是蠻合理的？」

助理判斷這個模型合理：Workspace → Project → Issue 對應工作歸屬, 空間內的成員權限能決定誰可以邀請。使用者日常只需要進專案處理工作, 不必每次操作都設定權限

建議第一版沿用簡單的管理者／一般成員：管理者邀請、管理成員, 一般成員加入後協作專案與 Issue。擁有者的移轉與最後管理者保護仍需定義, 不先擴成自訂角色編輯器

## Workspace 與專案的兩層權限

### 本輪確認與偏好

使用者提出同一 Workspace 有 100 個專案, 必須能逐專案設定誰能看、誰不能看；同時偏好 Workspace admin 可以查看所有專案, 方便委託他管理整個空間

- 加入 Workspace 取得空間成員資格, 專案存取再依各專案設定判斷
- Workspace admin 對該空間所有專案有可見性, 包含私人專案；私人是相對一般成員的限制, UI 應明確告知管理員仍可查看
- 這項例外只適用同一 Workspace, 不因 A 空間是 admin 而取得 B 空間權限
- 「看得到全部專案」已收斂, admin 是否也能修改全部 Issue、改成員或刪除專案等操作仍需另外定義

### 建議的專案可見性（待確認）

| 模式 | 一般空間成員 | 指定專案成員 | Workspace admin |
| --- | --- | --- | --- |
| 空間內可見 | 可以查看 | 可以查看, 依專案角色決定能做哪些操作 | 可以查看 |
| 私人／指定成員 | 未被加入專案則看不到 | 可以查看, 依專案角色決定能做哪些操作 | 可以查看 |

「空間內可見」只給這個 Workspace 的有效成員, 不代表網際網路公開。可見性決定能不能讀取, 專案角色再決定能不能新增／修改 Issue、留言、填工時或管理專案；角色名稱與矩陣尚待確認

建議新專案預設私人, 建立者取得專案管理權, 再按需要加入同伴或改成空間內可見。這是較保守的預設提案, 使用者尚未選定；既有共享專案不能在未討論遷移方式前直接改成私人

### 建議的權限判斷順序（待確認實作）

1. 確認登入身分, 並且仍是目標 Workspace 的有效成員；移除／停用後沒有任何該空間專案權限
2. 確認專案屬於目前 Workspace, 才繼續判斷
3. 若為該 Workspace 的 admin, 允許查看專案
4. 其他成員依專案可見性與指定成員資格判斷, 沒有取得讀取資格就拒絕
5. 查看之外的操作再檢查對應的空間／專案角色權限, 不因能看就一律能改

這樣 Workspace 層提供管理員的全專案可見性, 專案設定負責一般成員的可見範圍。建議第一版只用授權名單, 不再加入「明確拒絕」或每人覆蓋規則, 避免和 admin 例外互相衝突

例如：A 空間有 100 個私人專案, Mei 被加入其中 3 個, 就只看到這 3 個；Josh 是 A 空間 admin, 可以看到全部 100 個。Josh 被降為一般成員後, 重新依專案設定判斷；原本專案名單與可見性仍保留, 不因升降角色而被重寫

### 權限需要一起涵蓋的資料

專案列表、搜尋、深連結、Issue／Epic、留言、依賴、工時分析、匯出、通知與共享視圖都要套同一套專案讀取檢查。不可只隱藏專案卡片, 卻讓人從另一個 API、報表總數或通知看到私人專案名稱、內容與工時

現有常用視圖的「團隊共用」應縮小為同 Workspace 且有該專案讀取資格的人可用, 視圖作者修改權仍獨立檢查。admin 能看專案不代表能改寫別人的個人視圖或代改他人工時；這些專項規則另行決定

建議專案設定頁顯示每人的有效權限與來源, 例如「因 Workspace admin 可查看」或「由專案成員取得」。授權變更需留操作者與時間, 移出空間後專案授權立即失效；既有留言／工時保留作者紀錄

100 個專案的管理可先提供可搜尋的成員選擇、專案列表與批次指派。部門／群組授權可以後續加入, 不需要第一版就建立自訂權限引擎。這些都是管理體驗建議, 尚未定案或實作

### 固定角色或自訂角色（建議／待確認）

使用者問這兩層是否需要自訂身分, 或設定幾組固定身分就夠。這裡用「角色」表示成員在某個空間／專案能做什麼, 帳號仍是同一個登入身分

建議第一版兩層都採固定角色, 先提供以下組合：

| 層級 | 角色提案 | 用途與邊界 |
| --- | --- | --- |
| Workspace | 擁有者 Owner | 空間最終管理責任, 包含擁有權移轉與刪除空間等操作；付款權另議 |
| Workspace | 管理員 Admin | 邀請／管理成員及空間設定, 依已確認方向可查看所屬空間全部專案 |
| Workspace | 成員 Member | 在有資格查看的專案中參與工作, 不取得空間管理權 |
| Project | 專案管理者 Manager | 管理此專案設定、成員與工作, 不因此取得 Workspace admin 權限 |
| Project | 協作者 Contributor | 新增／修改 Issue、留言、登記自己的工時, 不管理專案權限 |
| Project | 唯讀者 Viewer | 查看允許的專案內容, 不修改 Issue、留言或登記工時 |

具體矩陣仍待確認, 包含誰可建立專案、任命 admin、停用他人、刪除 Issue／專案, 以及 admin 是否可修改未加入專案的 Issue。可查看專案的例外不自動擴成所有操作都允許

同一人可以是 Workspace member、A 專案管理者、B 專案唯讀者, 並且看不到私人 C 專案。授權時只需選固定角色, 不要求管理員逐項勾選 API 權限

專案管理者可加入的對象建議限該 Workspace 現有成員；邀請空間外的人需要另有 Workspace 邀請權。這是授權邊界建議, 尚未定案。專案角色也不改變既有私有視圖作者權限與只能修改自己工時的規則, 除非之後另行決定

採固定角色可以讓設定畫面、權限說明、測試與問題追查保持一致。100 個專案的規模主要是批次指派／群組管理的需求, 本身不代表需要自訂角色

後端建議把操作權限集中定義, 例如邀請成員、讀取專案、編輯 Issue, 由固定角色映射, 避免在各處散落角色名稱判斷。未來若出現「可管任務但不可看團隊工時」等固定組合無法表達的需求, 再評估自訂角色介面與授權限制；目前不實作任意勾選權限或每人例外

前輪的管理者／一般成員提案較粗, 本輪因已有專案可見性需求而細分為上述固定角色提案, 並未取得使用者採納。現有程式仍只有空間 admin／member, 這六組角色尚未實作

### 角色與權限如何判斷（具體架構提案, 待採納）

使用者明確要求先設計清楚, 不想模糊試作後又大改。建議確立：**角色提供一組權限, 業務操作檢查權限及資源條件, 不直接比對角色名稱**

固定角色是管理介面的第一版選項；集中授權是從第一版就採用的實作結構。自訂角色未來只擴充權限組合的來源, 業務操作可以繼續使用同一個授權入口。新增特殊資源規則仍可能需要修改 policy 與測試, 不承諾之後完全不用改程式

#### 三個概念分開保存

| 項目 | 提案契約 | 用途 |
| --- | --- | --- |
| 顯示名稱 | 例如「工作空間管理員」, 可以改名或翻譯 | 只供畫面呈現, 不參與授權 |
| 固定角色 ID | 例如 workspace.admin、project.contributor, 有明確 scope | 指向權限組合, 不用大小／排序代表權限高低 |
| 操作權限 ID | 例如 workspace.members.invite、project.read、issue.update | 由授權服務判斷是否可對目標資源執行 |

初期角色定義與權限映射可集中在程式碼的一個 registry, 不必現在做自訂角色資料表或設定介面。成員紀錄保存 roleId, 避免把一整份權限複製到每個帳號, 以免定義修改後產生不同版本

Membership 保存 workspaceId、userId、roleId、status；ProjectMember 保存 projectId、userId、roleId, 並要求帳號仍是專案所屬空間的有效成員。角色定義包含 id、scope、label 與 permissionIds。跨空間角色或無效角色一律不產生授權

#### 操作只呼叫統一入口

以下是契約示意, 尚未實作：

```js
authorize(context, 'workspace.members.invite', workspaceResource);
authorize(context, 'project.read', projectResource);
authorize(context, 'issue.update', issueResource);
authorize(context, 'timeEntry.updateOwn', timeEntryResource);
```

context 的使用者來自已驗證 session, 角色與有效成員資格由後端當次讀取。resource 由後端以 ID 查回, 解析真實的 projectId／workspaceId／作者；不信任前端送入的 permissionIds、角色、作者或空間歸屬

畫面可用同一政策推導的 can／capabilities 決定按鈕是否呈現, 每次真正 API 操作仍重新授權。session 不保存可長期獨立生效的權限快照, 第一版不加入跨請求授權快取, 避免降權或移除後舊權限繼續可用

#### 適用範圍與規則是明確的

| 權限例子 | 賦予來源提案 | 執行時額外條件 |
| --- | --- | --- |
| workspace.members.invite | Workspace Owner／Admin | 只對該空間, 能授予的角色另定, 不能任意升權 |
| project.readAny | Workspace Owner／Admin | 只在該空間內授權所有專案讀取, 不代表任意資料／操作都可讀寫 |
| project.read | Project Manager／Contributor／Viewer | 只對有專案角色的那個專案 |
| issue.update | Project Manager／Contributor | Issue 屬於該專案, 且專案可讀, 保存時仍驗證 Issue revision |
| timeEntry.updateOwn | Project Manager／Contributor | 所屬專案可讀, 且 entry.userId 必須是操作者, 非作廢紀錄 |
| savedView.updateOwn | 另定對應操作角色 | 所屬專案可讀, 且作者為操作者；團隊分享不授予修改權 |

上述角色映射是提案示例, admin 能讀全部專案則是 D-011 已確認方向。admin 是否另有修改全部專案、替他人修改工時、刪除專案等權限尚未決定, 不能以 admin 名稱直接放行

對「空間內可見」專案, policy 可替有效 Workspace 成員提供該專案的基礎讀取資格, 並記錄來源是 visibility。這不會自動授予 issue.update 或成員管理權；若需其他操作, 必須有對應專案角色／明確政策

#### 統一判斷順序

1. 驗證登入, 從可信資料解析目標資源的 Workspace 與專案
2. 檢查空間一致及成員仍有效, 失敗就拒絕, 任何角色都不能跨過這個邊界
3. 按目標範圍展開 Workspace 角色與該 Project 角色的有效權限；未知 permission ID／role ID 預設拒絕
4. 讀取專案時, project.readAny（同空間）、project.read（該專案）、空間內可見三個來源任一成立才允許
5. 執行其他操作時, 另檢查所需操作權限與作者／狀態等資源條件；可見性本身不提供寫入權
6. 寫入在同一交易內重讀授權與 revision, 再進行異動, 確保授權檢查和資料寫入一致

已完成項目的重試也先重新授權, 才能讀取 requestId 對應結果。成員被移除或失去專案權限後, 不可用舊 requestId 讀回私人資料。列表／統計與單筆 API 共用政策判斷, 不只在詳細內容擋權限

第一版採範圍內的權限授予, 沒有每人 deny 例外或通用星號權限；空間／作者條件不能被一般 grant 略過。admin 的讀取來源是 project.readAny 的明確規則, 不使用「admin 一律通過」的全域捷徑

角色指派與 admin 提升須使用獨立管理政策及可授予角色名單；擁有權移轉也須獨立驗證, 不能因某人能邀請或修改普通成員就取得升權能力。正式可授予角色矩陣仍待確認

#### 現有程式的實際差距與遷移順序

本輪盤點發現目前原型仍有直接角色判斷：server/auth.js 的 invite, server/app.js 的 SMTP verify, src/domain/service.js 的狀態設定與通知可見性。視圖與工時另有作者檢查, getWorkspace 尚未按專案 ACL 過濾。這些不能因文件寫了 authorize 就算已完成

建議在實作專案 ACL 前一次整理以下範圍：

1. 先確認權限目錄與固定角色矩陣, 特別是 admin 可讀／可改界線、誰能建專案與授權角色
2. 建立集中 policy／authorize 與資源解析, 先以矩陣測試驗證, 呼叫端只依 permission ID 授權
3. 在同一個功能階段接齊 API 與列表／統計／通知／重試結果, 移除散落的 role === admin 判斷, 保留作者限制與業務狀態規則
4. 明確遷移舊 admin／member 與既有共享專案, 不把成員靜默升權, 也不突然改成私人造成資料無法存取

SMTP 目前是整個本機服務的設定, 遷移時須區分部署級 SMTP 管理與 Workspace 邀請權, 不讓新權限映射把空間管理者直接變成整個部署的管理者。SaaS 與自建共用同一組 policy 契約, 供應商／部署能力由 adapter 或明確能力設定補充

#### 實作前要通過的驗收情境

- 同樣顯示名稱但不同 roleId, 只按各自權限生效；改名／翻譯不影響授權
- 同一人管理 A 空間, 無法讀取 B 空間, 也不能用 B 空間 ID 或其他專案角色混入權限
- Workspace admin 可讀取私人專案, 缺少 issue.update 時仍不能修改該專案 Issue
- 一般成員可讀空間內可見專案, 沒有操作權限就不能寫；加入專案 Contributor 後取得該專案編輯權
- Contributor 可修改自己的有效工時, 不能代改他人；admin 的全專案可見性不繞過此條件
- 降權／退出空間後, 下一次 API 與舊 requestId 重試都不能繼續取得已失權資料
- 搜尋、統計、通知與共享視圖不能洩漏不可讀專案內容；未知權限／角色與無效資源預設拒絕

依據與界線：以上為 TaskTracker 的具體提案, 尚未改程式。[NIST RBAC](https://csrc.nist.gov/projects/role-based-access-control) 提供使用者、角色與權限分離的模型；[OWASP 授權指引](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) 建議預設拒絕、每次請求驗證授權, 並依資源屬性／關係補充判斷。因此此處採角色提供權限＋空間／專案／作者條件, 單純檢查有無某個權限字串仍不足以完成資源授權

## 目前正在收斂：帳號、個人與企業

### 企業如何讓成員加入

使用者提出兩個選項：

| 選項 | 使用者看到的流程 | 需要釐清的地方 |
| --- | --- | --- |
| A. 企業註冊後設定可登入信箱 | 管理員填哪些 Email 可以進入 | 填入 Email 之後, 使用者如何驗證本人身分、建立帳號與啟用權限？ |
| B. 使用者各自註冊, 企業邀請加入 | 每人有自己的帳號, 再取得企業成員資格 | 是否一定要先註冊才能被邀請？同一帳號能否參與多個企業？ |

**目前建議／待確認：採獨立帳號＋工作空間成員資格, 管理員可先填 Email 邀請, 收到邀請的人不必事先註冊**

理由：保留管理員管理名單的便利, 又讓每個人維持自己的登入身分。同一個人可以參與公司、客戶或其他團隊, 在各空間有不同權限

建議流程：

1. 第一位使用者建立帳號與工作空間, 成為擁有者
2. 管理員輸入 Email 並指定邀請角色
3. 受邀者開啟邀請連結：沒有帳號就完成註冊與信箱驗證, 已有帳號就登入對應身分
4. 接受邀請後建立成員資格, 才取得該空間權限
5. 登入後可以選擇／切換自己加入的工作空間

信箱允許名單、公司網域限制可以是後續的加入政策, 單純填入 Email 不代表已驗證持有者, 也不應直接開放企業資料。是否支援這些政策、是否強制 SSO 尚未決定

### 沒有企業邀請的人是什麼身分

使用者接著問：「個人使用者應該也要有一些功能嗎？如果純註冊但沒有企業邀請, 這個人算什麼？」

**目前建議／待確認：這個人是平台使用者, 可以建立自己的工作空間, 用來管理個人專案**

- 個人使用者可以建立專案、任務、Epic 與看板, 記錄／分析自己的工時, 保存個人常用視圖
- 工作空間只有自己時就作為個人空間使用；之後需要合作, 可以邀請成員使用同一批專案
- 同一帳號可同時擁有個人空間, 並加入企業空間, 資料依空間分開
- 角色屬於成員資格：同一個人在個人空間可能是擁有者, 在公司是一般成員
- 「個人帳號／企業帳號」暫不設為互斥的固定帳號類型；正式方案、額度與收費另討論

這是助理針對使用者問題提出的方向, 尚未取得使用者明確採納, 不視為已定案功能範圍

## 核心概念提案

| 概念 | 負責的事情 | 例子 |
| --- | --- | --- |
| Account 帳號 | 平台登入身分 | Josh 用自己的 Email 登入 |
| Workspace 工作空間 | 專案與團隊資料的歸屬及隔離邊界 | Josh 的工作空間、A 公司、B 客戶 |
| Membership 成員資格 | 帳號在某個空間的角色與啟用狀態 | Josh 在 A 公司是成員, 在自己的空間是擁有者 |
| Invitation 邀請 | 接受前的加入資格, 含受邀 Email、期限與角色 | A 公司邀請 Josh 加入 |
| Project 專案 | 屬於一個空間的工作集合 | A 公司空間裡的官網改版 |
| Issue 工作項目 | 屬於一個專案的追蹤項目 | 官網改版專案裡的登入 Task 或 Bug |

前三種概念目前程式已分開保存；多空間與邀請角色是擴充提案, 不能因此宣稱已支援所有情境

從企業移除成員時, 建議撤銷該空間權限, 保留任務、留言與工時的作者紀錄, 不直接刪除其平台帳號或其他空間資料。實際停用、擁有權移轉與資料保留流程尚待討論

## SaaS 與自建版本

使用者指出：「這樣切的話 SaaS 版本跟自建版本應該也會好切」

助理判斷 Workspace → Project → Issue 與空間內成員資格有利共用核心模型。建議維持同一套程式與資料結構, 以部署設定與 adapter 處理差異, 減少長期維護兩套業務規則的成本

| 項目 | SaaS 部署提案 | 自建部署提案 |
| --- | --- | --- |
| 核心功能 | Workspace、專案、Issue、工時與成員權限 | 沿用相同功能與授權規則 |
| 註冊／加入政策 | 可開放註冊並建立／加入空間 | 可設定僅邀請或由部署管理者初始化, 預設尚未定 |
| 空間數量 | 同一服務容納多個獨立工作空間 | 可以先用一個空間, 仍保留空間 ID 與隔離, 不移除資料層級 |
| 郵件／登入／儲存 | 由服務營運者設定供應商及部署資源 | 由自建維運者提供環境設定與必要服務 |
| 方案／帳務 | 需要時加在服務營運層 | 是否提供授權／額度限制另定, 不讓核心 Issue 操作依賴雲端帳單 |
| 升級與備份 | 服務營運者維護 | 自建維運者負責, 需提供版本遷移與備份／復原說明 |

建議把「整個部署的管理者」與「某個 Workspace 的管理者」分開定義。管理自己的空間不等於能管理其他客戶資料或部署設定；正式角色與後台權限尚未決定

容易分開部署不代表只要一個版本開關就完成交付, 後續仍須驗證設定、資料遷移、升級與外部服務依賴。目前 Compose 是本機開發設定, 尚未提供正式自建版安裝／升級套件；GAS 產檔仍依原約定暫緩, 兩版本方向未自動取代原先 GAS 評估

本節除了 D-009 的設計目標外, 都是實作與交付建議, 尚待確認

## 現有原型與提案的差距

依目前帳號實作核對, 這些是現況, 不是新規格已完成：

| 項目 | 目前原型 | 待補的方向 |
| --- | --- | --- |
| 自行註冊 | 建立帳號時同時建立一個有名稱的空間, 角色為 admin | 拆開註冊與引導, 是否需要 owner 角色 |

| 郵件 | 指派／留言預覽與 SMTP verify, 邀請靠複製連結 | 真實寄送與失敗處理, 尚未啟用 |
