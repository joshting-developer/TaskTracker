# TaskTracker 產品討論紀錄

建立／最後更新：2026-10-19（Asia/Taipei）

這份文件持續整理我們的產品討論, 作為下一輪討論與實作的共同入口。使用者要求邊討論邊更新, 避免決策、問題與理由只留在聊天裡

## 如何維護

- 每輪有新的需求、選項、決策或修正, 同步更新對應章節與最後更新日期
- 使用者明確採納才標「已確認」；助理提出的方案標「建議／待確認」, 不把追問或沒有反對當成同意
- 「已實作」只描述目前原型行為, 不代表正式產品規則已定案
- 改變方向時記錄原方案、新方案與原因, 舊紀錄保留在討論沿革, 不讓兩份矛盾規格同時生效
- 功能細節連到專門設計文件, 本文件保留產品決策與理由；決策確認後再同步受影響的文件與實作
- 純產品討論先整理文件, 是否實作依當輪指示與既有授權判斷

## 已確認的主要操作流程

使用者確認：「workspace → 建立專案 → 專案可以開 issue」

```text
Workspace 工作空間
└─ Project 專案
   └─ Issue 工作項目
```

操作順序：進入工作空間 → 建立或選擇專案 → 在該專案新增 Issue, 並使用清單、看板與詳細內容管理工作

- 工作空間整理它所屬的專案, 可以包含多個專案
- 專案整理它所屬的 Issue, 可以包含多個 Issue
- 每個專案屬於一個工作空間, 每個 Issue 屬於一個專案
- 新增 Issue 時固定目前專案, 個人或團隊使用都沿用這個層級；個人功能範圍仍待確認
- 目前原型的 Task、Bug、Feature、Epic 都是 Issue 類型；Epic 與子任務的關係發生在專案內, 不增加專案上方的層級

已確認工作流程、資料層級及邀請須有權限。帳號如何建立／取得工作空間、能否加入多個空間、成員角色與具體邀請政策仍按下方待討論項目處理

## 已確認：邀請需要權限

使用者補充：「有權限的帳號或者說有權限的 Workspace 可以去邀請使用者加入」

已確認的要求是邀請入口與操作須有授權, 不是所有註冊帳號都能邀請他人進入任意 Workspace

建議將規則表達為：**帳號在指定 Workspace 具備「邀請成員」權限, 才能代表該 Workspace 邀請使用者加入**

- 帳號是操作的人, Workspace 是邀請所屬的空間, 邀請指向明確的 Workspace
- 建議以帳號在該空間的成員資格／角色判斷權限, A 空間的權限不延伸到 B 空間
- 建立邀請時由後端檢查授權, 隱藏前端按鈕只負責操作體驗
- 「可以邀請」與「可以給受邀者哪些角色」分開定義, 本輪尚未授權邀請者任意提升他人權限
- 目前原型僅 admin 可邀請, 是現有行為；正式要給 owner／admin 或自訂角色哪些權限仍待確認
- 如果「有權限的 Workspace」也包含空間方案／設定允許邀請的意思, 可再加空間層級開關；是否需要這一層還沒決定

這項確認沒有一併決定受邀者是否必須先註冊、個人空間額度、多空間切換或加入後的專案存取範圍, 這些保留在待討論清單

## 目前正在收斂：帳號、個人與企業

### 企業如何讓成員加入

使用者提出兩個選項：

| 選項 | 使用者看到的流程 | 需要釐清的地方 |
| --- | --- | --- |
| A. 企業註冊後設定可登入信箱 | 管理員填哪些 Email 可以進入 | 填入 Email 之後, 使用者如何驗證本人身分、建立帳號與啟用權限？ |
| B. 使用者各自註冊, 企業邀請加入 | 每人有自己的帳號, 再取得企業成員資格 | 是否一定要先註冊才能被邀請？同一帳號能否參與多個企業？ |

**目前建議／待確認：採獨立帳號＋工作空間成員資格, 管理員可先填 Email 邀請, 收到邀請的人不必事先註冊**

理由：保留管理員管理名單的便利, 又讓每個人維持自己的登入身分。同一個人可以參與公司、客戶或其他團隊, 在各空間有不同權限

建議流程：

1. 第一位使用者建立帳號與工作空間, 成為擁有者
2. 管理員輸入 Email 並指定邀請角色
3. 受邀者開啟邀請連結：沒有帳號就完成註冊與信箱驗證, 已有帳號就登入對應身分
4. 接受邀請後建立成員資格, 才取得該空間權限
5. 登入後可以選擇／切換自己加入的工作空間

信箱允許名單、公司網域限制可以是後續的加入政策, 單純填入 Email 不代表已驗證持有者, 也不應直接開放企業資料。是否支援這些政策、是否強制 SSO 尚未決定

### 沒有企業邀請的人是什麼身分

使用者接著問：「個人使用者應該也要有一些功能嗎？如果純註冊但沒有企業邀請, 這個人算什麼？」

**目前建議／待確認：這個人是平台使用者, 可以建立自己的工作空間, 用來管理個人專案**

- 個人使用者可以建立專案、任務、Epic 與看板, 記錄／分析自己的工時, 保存個人常用視圖
- 工作空間只有自己時就作為個人空間使用；之後需要合作, 可以邀請成員使用同一批專案
- 同一帳號可同時擁有個人空間, 並加入企業空間, 資料依空間分開
- 角色屬於成員資格：同一個人在個人空間可能是擁有者, 在公司是一般成員
- 「個人帳號／企業帳號」暫不設為互斥的固定帳號類型；正式方案、額度與收費另討論

這是助理針對使用者問題提出的方向, 尚未取得使用者明確採納, 不視為已定案功能範圍

### 註冊後的入口提案

| 情境 | 建議行為 | 狀態 |
| --- | --- | --- |
| 自行註冊, 沒有邀請 | 引導建立第一個工作空間, 可預填「Josh 的工作空間」 | 待確認 |
| 從邀請連結註冊 | 直接完成加入受邀空間, 不強迫多建一個個人空間 | 待確認, 新帳號加入已有原型 |
| 已有帳號接受邀請 | 登入對應帳號後接受, 加入同一空間 | 待實作, 產品流程待確認 |
| 已有帳號想管理個人專案 | 可以新增自己的工作空間 | 待確認／待實作 |
| 有多個工作空間 | 顯示切換入口, 每次操作由後端確認目前空間權限 | 待確認／待實作 |
| 沒有任何空間成員資格 | 顯示建立空間／查看待接受邀請的引導 | 待確認／待實作 |

尚未決定註冊後要自動建立空間, 還是讓使用者完成命名後才建立。目前建議採引導建立, 不讓受邀者無故多出一個未使用的空間

## 核心概念提案

| 概念 | 負責的事情 | 例子 |
| --- | --- | --- |
| Account 帳號 | 平台登入身分 | Josh 用自己的 Email 登入 |
| Workspace 工作空間 | 專案與團隊資料的歸屬及隔離邊界 | Josh 的工作空間、A 公司、B 客戶 |
| Membership 成員資格 | 帳號在某個空間的角色與啟用狀態 | Josh 在 A 公司是成員, 在自己的空間是擁有者 |
| Invitation 邀請 | 接受前的加入資格, 含受邀 Email、期限與角色 | A 公司邀請 Josh 加入 |
| Project 專案 | 屬於一個空間的工作集合 | A 公司空間裡的官網改版 |
| Issue 工作項目 | 屬於一個專案的追蹤項目 | 官網改版專案裡的登入 Task 或 Bug |

前三種概念目前程式已分開保存；多空間與邀請角色是擴充提案, 不能因此宣稱已支援所有情境

從企業移除成員時, 建議撤銷該空間權限, 保留任務、留言與工時的作者紀錄, 不直接刪除其平台帳號或其他空間資料。實際停用、擁有權移轉與資料保留流程尚待討論

## 現有原型與提案的差距

依目前帳號實作核對, 這些是現況, 不是新規格已完成：

| 項目 | 目前原型 | 待補的方向 |
| --- | --- | --- |
| 自行註冊 | 建立帳號時同時建立一個有名稱的空間, 角色為 admin | 拆開註冊與引導, 是否需要 owner 角色 |
| 邀請新帳號 | 管理員產生七日單次邀請連結, Email 需相符, 註冊後角色為 member | 信箱驗證、可選角色、邀請狀態管理 |
| 邀請已有帳號 | 尚未支援接受流程, 註冊會遇到 Email 已使用 | 登入後接受邀請 |
| 一帳號多空間 | 登入只選到第一個成員空間, 沒有切換 API／畫面 | 建立其他空間、空間清單與切換 |
| 沒有任何成員資格 | 登入目前會回報找不到工作空間資格 | 允許平台登入後走空間引導 |
| 成員停用／角色 | 只有 admin／member, 沒有完整停用與角色管理 | 明確角色權限、撤銷、最後擁有者保護 |
| 專案資料權限 | 空間間隔離, 空間內專案與工時先共享 | 私人專案與專案角色權限 |
| 郵件 | 指派／留言預覽與 SMTP verify, 邀請靠複製連結 | 真實寄送與失敗處理, 尚未啟用 |

實作依據：[帳號與邀請](../server/auth.js)、[協作設計](collaboration-design.md)。原型可讓一人管理專案, 但目前沒有完整的個人／團隊方案區分
