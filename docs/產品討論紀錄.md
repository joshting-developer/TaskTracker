# TaskTracker 產品討論紀錄

建立：2026-10-19／最後更新：2026-11-04（Asia/Taipei）

這份文件持續整理我們的產品討論, 作為下一輪討論與實作的共同入口。使用者要求邊討論邊更新, 避免決策、問題與理由只留在聊天裡

## 如何維護

- 每輪有新的需求、選項、決策或修正, 同步更新對應章節與最後更新日期
- 使用者明確採納才標「已確認」；助理提出的方案標「建議／待確認」, 不把追問或沒有反對當成同意
- 「已實作」只描述目前原型行為, 不代表正式產品規則已定案
- 改變方向時記錄原方案、新方案與原因, 舊紀錄保留在討論沿革, 不讓兩份矛盾規格同時生效
- 功能細節連到專門設計文件, 本文件保留產品決策與理由；決策確認後再同步受影響的文件與實作
- 純產品討論先整理文件, 是否實作依當輪指示與既有授權判斷

## 2026-11-04 後端可讀性與暫緩重構

已確認：使用者決定後端架構之後再處理，並指出目前程式對人工閱讀非常不友善。本輪只記錄，不修改後端程式、API 或資料結構。

目前實作：Laravel 已負責登入／Session／CSRF、交易與 migration；業務仍沿用 RPC 分派、集中式 WorkspaceService，以及 records 表中的 JSON payload。多個業務責任集中、密集單行寫法與缺少明確領域模型，使閱讀及追查成本偏高，不能把程式行數少視為容易維護。

後續建議，尚未核定具體重構方案：依業務拆分 Controller／Service，展開流程並使用清楚命名，建立可理解的資料模型與關聯，讓請求驗證、授權、業務操作與回應邊界清楚。目標是讓開發者能從入口追到規則與資料，不需先理解整個通用分派器；重構需保留既有權限、租戶隔離、revision、防重複提交及資料遷移保護。

## 已確認的主要操作流程

使用者確認：「workspace → 建立專案 → 專案可以開 issue」

```text
Workspace 工作空間
└─ Project 專案
   └─ Issue 工作項目
```

操作順序：進入工作空間 → 建立或選擇專案 → 在該專案新增 Issue, 並使用清單、看板與詳細內容管理工作

- 工作空間整理它所屬的專案, 可以包含多個專案
- 專案整理它所屬的 Issue, 可以包含多個 Issue
- 每個專案屬於一個工作空間, 每個 Issue 屬於一個專案
- 新增 Issue 時固定目前專案, 個人或團隊使用都沿用這個層級；個人功能範圍仍待確認
- 目前原型的 Epic、Task、Bug 都是 Issue 類型（依 D-022 收斂, 舊 Feature 改為 Task）；Epic 與子任務的關係發生在專案內, 不增加專案上方的層級

已確認工作流程、資料層級及邀請須有權限。帳號如何建立／取得工作空間、能否加入多個空間、成員角色與具體邀請政策仍按下方待討論項目處理

### 最新確認與本輪實作

使用者確認兩類關係並取消前置, 本輪具體選擇如下, 不將細節都宣稱為使用者逐項指定：

- **子任務**：同專案一層, Task／Bug／Feature 均可作父項或子項。父項直接輸入標題新增子任務；既有任務可設定／解除父任務。子項仍是獨立 Issue, 可指派、填估時／工時、在列表／看板操作, 不是文字 checklist
- **關聯任務**：按「新增關聯」才搜尋及選取目標, 平常只顯示已建立關係。兩端同步顯示, 任一端可解除, 不自動連動狀態。只限同專案其他 Issue, 含 Epic
- **狀態**：一般父任務顯示子項完成數, 可獨立結案／重開, 子項也獨立管理；不因子項完成／重開自動更改父狀態。移除前置的結案阻擋與相關提示／篩選
- **Epic 與工時**：子任務隨父項 Epic, 父項改 Epic 時交易內同步子項與版本／歷史。一般父項工時只算自身, Epic 按每個實際 Issue 加一次, 避免父項彙總再加子項造成重複。既有 Epic 人工驗收及取消語意保留
- **舊資料**：前置邊轉成一般雙向關聯, 不猜成父子；ID、狀態、原作者、歷史及工時保留, 新增升級歷史並增加 revision。升級前備份, 之後的舊版匯入也用同一升級器
- **舊視圖**：blocked／review 條件保留並標示已停用, 結果為空, 明確改條件後才可更新, 不悄悄放寬搜尋

完整契約、升級及相容規則見[日常流程](workflow-design.md)。這是本機版本, Project ACL／正式角色矩陣仍未完成；不額外加入自訂關係型別、任意深度階層或 workflow 引擎

### 官方事實（查閱 2026-10-20）

YouTrack 提供不同語意的 Issue links：`relates to` 表示一般關聯, `subtask of`／`parent for` 表示父子拆解, `depends on`／`is required for` 表示有方向的依賴。關係會在兩端呈現。使用者透過 Add links 選類型、搜尋既有 Issue, 也能直接建立有連結的新 Issue；以 parent for 建立的新 Issue 是目前任務的子任務。[Link Issues](https://www.jetbrains.com/help/youtrack/cloud/link-issues.html)

「有未完成依賴就禁止轉 Fixed」是 Dependencies workflow 的規則, 官方標示 Auto-attached: no, 不應把依賴連結本身說成所有專案一律強制的結案規則。[Dependencies workflow](https://www.jetbrains.com/help/youtrack/cloud/workflow-dependencies.html)

另有 Subtasks workflow, 官方標示 Auto-attached: yes, 可在子任務重開時重開父任務、全部完成時將父任務轉 Fixed。這是該 workflow 的自動化行為, 不代表 TaskTracker 必須照搬。[Subtasks workflow](https://www.jetbrains.com/help/youtrack/cloud/workflow-subtasks.html)

## Workspace 與專案的兩層權限

### 已確認的 Workspace 角色與專案存取

| Workspace 角色 | 定義 | 專案權限來源 |
| --- | --- | --- |
| owner | 建立 Workspace 的人 | 可操作該空間所有專案, 不須逐一加入 Project |
| manager | 協助管理 Workspace 的人 | 可操作該空間所有專案, 不須逐一加入 Project |
| user | 一般使用者 | 預設無專案可見性與操作權；須加入 Project 並取得對應授權 |

owner 與 manager 的專案操作範圍相同, 都只適用自己所屬的 Workspace。兩者在空間刪除、擁有權移轉、任命其他 manager 等空間層級的差異尚待定義。user 即使已加入 Project, 仍需對應操作權限, 不代表加入就全部可做

以上描述各預設角色應包含的權限組合。實作時全專案操作資格來自被授予的範圍權限, 不因角色叫 owner 或 manager 就另走放行捷徑；Project 成員資格也只提供授權範圍, 不自動附送所有操作權限

#### 負責人和 PM 的差別

建議用責任歸屬理解負責人：目前由誰承擔這個專案的交付責任。公司老闆可以擔任, 也可以交給部門主管或其他人, 不必強制掛老闆；PM 則是日常安排與協調的人。兩個職責可以由同一個人承擔

負責人是 Project 層級的責任, 與建立 Workspace 的 owner、每張 Issue 的負責人 assignee 都要分開。交接專案責任不應自動轉移 Workspace 擁有權, 也不必把每張 Issue 全部改指派給新負責人

負責人與 PM 可以先共用多數專案操作權限, 不為了名稱不同就硬造一套角色高低繼承；要不要把指定 PM、責任交接或重要驗收設成負責人的專屬權限, 必須另列在矩陣。負責人是單一主要責任人或允許多人、是否須接受交接, 目前尚未決定

#### 讀者的用途與資料範圍

讀者可以用於只需看進度的主管、稽核人員, 或核對特定專案投入的財務／人資。這些是使用情境, 不代表只要職務是財務／人資就自動能看所有專案或所有資料

建議分開定義以下權限, 名稱是 permission ID 提案：

- project.read／issue.read：專案進度、Issue、Epic 與看板的讀取
- timeReport.read：該專案工時彙總的讀取
- timeEntry.readTeam：該專案成員逐筆工時與說明的讀取
- project.export／timeReport.export：對應資料的匯出, 同時要求該資料原本就可讀

Reader 基本可查看專案進度, 工時分析、逐筆明細與匯出應分開在預設矩陣決定。將來若核對資料的人需要不同組合, 再評估報表角色或自訂角色, 不先把全資料閱覽綁在 Reader 名稱上。未來若只有資料類別權限不同, 可以透過集中 policy 處理, 仍須實測 API 與報表輸出範圍

#### 作用範圍與尚待定義的操作

Project 角色只對被加入並授權的專案生效。專案 PM 管理成員時建議限既有 Workspace 成員, 邀請空間外帳號須另外有 workspace.members.invite；不能提升 Workspace 角色。可授予的專案角色、能否更換負責人仍待定

同一個 Workspace user 可以在 A 專案負責、B 專案只讀, 並且看不到 C 專案。Workspace owner／manager 則依已確認的空間級權限操作所有專案, 不必逐案取得上述角色

資料刪除、代改工時、責任交接、匯出與閱讀明細的條件需明列, 不直接將「負責人」當作任意資料操作通行證。正式角色 ID 與顯示名稱待確認；程式仍按 permission ID＋資源 scope＋條件判斷

前輪助理曾提出 project.manager／contributor／viewer 與三角色基本矩陣, 現改由上述四角色作為討論基礎。尚未實作 Project 角色, 不需遷移已部署的三角色資料

UI 應明確告知：限制專案成員的設定適用於 user, owner／manager 仍可操作空間內全部專案。角色升降不重寫各專案名單；manager 降為 user 後, 改依既有 Project 成員資格與授權判斷

### 與「空間內可見」的比較與選擇

| 情境 | 使用者選定的版本 | 前輪「空間內可見」提案 |
| --- | --- | --- |
| user 加入 Workspace, 還沒加入任何 Project | 看不到任何專案, 無法操作 | 若某專案開放空間內可見, 不必加入該 Project 就能讀取 |
| user 被加入並授予專案讀取權 | 可以讀該專案, 其他操作依權限判斷 | 可以讀該專案, 其他操作仍依權限判斷 |
| user 從某個 Project 被移除 | 不再具有該專案存取資格 | 若該專案仍是空間內可見, 可能仍有基礎讀取資格 |
| owner／manager | 可操作所屬空間全部專案 | 不影響空間管理角色的全專案範圍 |

助理比較：明確加入＋授權適合逐專案限制成員；空間內可見能減少全團隊共用專案的逐人設定, 但新空間成員也會取得這類專案讀取資格。對 100 個需要區分成員的專案, 前者的授權來源較直觀

使用者已明確選定前者。第一版不提供空間內可見的授權來源, 不會因同網域、同 Workspace 或分享視圖就自動開放讀取。先前的兩種可見性模式與「新建預設私人」提案已被此決策取代, 舊提案保留於沿革

使用者認為以權限區分後未來較容易開放。後續若恢復空間內可見, 可在集中 policy 增加限該空間的讀取授予來源；仍須同步處理移出 Project 後的有效權限說明、查詢與測試, 不當作完全無需調整

### 權限需要一起涵蓋的資料

專案列表、搜尋、深連結、Issue／Epic、留言、依賴、工時分析、匯出、通知與共享視圖都要套同一套專案存取檢查。不能只隱藏卡片, 卻讓 user 從 API、報表總數或通知看到未授權專案內容

共享視圖只能給同空間且具備該專案讀取資格的人使用, 不會自己授予專案權限。既有私有視圖作者限制、工時是否能由管理者代改等資源專屬規則, 需在細項矩陣中明列；不能將「所有專案可操作」擴張為整個平台帳號、其他空間或部署設定的管理權

建議設定頁呈現權限來源, 例如「因 Workspace manager 取得全專案操作權」或「由專案成員資格與角色取得」。授權異動留操作者與時間, 移出 Workspace 後所有該空間 Project 授權失效, 既有工時／留言保留歷史作者

100 個專案可先提供搜尋與批次指派協助管理, 群組與自訂角色後續評估。舊原型仍是空間內共享, 遷移必須處理既有專案成員與舊 admin／member 角色, 不直接把舊 admin 改名為 owner 或把所有 user 加入所有 Project

### 角色與權限如何判斷（方向已採納, 細項待定）

使用者明確要求先設計清楚, 不想模糊試作後又大改。已確認採用：**角色提供一組權限, 業務操作檢查權限及資源條件, 不直接比對角色名稱**

使用者再次強調：「這些身分是擁有權限, 這些權限才真正控制哪些能看到、哪些看不到」。這是所有層級共同遵守的規則, 不因使用固定角色而改回角色判斷

```text
成員的角色指派
  → 解析該角色在此範圍授予的權限
  → authorize 檢查操作權限、資源範圍與條件
  → 決定可見資料與允許操作
```

- Role registry 可以根據 roleId 找權限組合, 但 authorize／業務流程不能用 roleId 或顯示名稱當作獨立通行證
- 相同角色可能指派在不同專案, 權限只在各自 scope 生效；相同有效權限、scope 與資源條件, 不因角色名稱不同而有不同結果
- 例如讀者的權限組合若之後加入匯出權限, 便能匯出原本可讀的指定資料, 不需要在匯出 API 補「允許 Reader」分支；目前尚未決定預設是否授予匯出
- 不得在按鈕、列表過濾或後端額外寫「是 PM／開發者才可以」, 必須對應到操作所需 permission ID；沒有權限就不能僅因職稱而放行
- 顯示名稱、責任歸屬與職務名稱不能自己產生存取權, 仍須有實際權限授予來源。第一版沒有因此新增個人任意覆寫或自訂角色功能

固定角色是管理介面的第一版選項；集中授權是從第一版就採用的實作結構。自訂角色未來只擴充權限組合的來源, 業務操作可以繼續使用同一個授權入口。新增特殊資源規則仍可能需要修改 policy 與測試, 不承諾之後完全不用改程式

#### 三個概念分開保存

| 項目 | 提案契約 | 用途 |
| --- | --- | --- |
| 顯示名稱 | 例如「工作空間管理員」, 可以改名或翻譯 | 只供畫面呈現, 不參與授權 |
| 固定角色 ID | 例如 workspace.owner、workspace.manager、workspace.user、project.developer（後者為候選 ID）, 有明確 scope | 指向權限組合, 不用大小／排序代表權限高低 |
| 操作權限 ID | 例如 workspace.members.invite、project.read、issue.update | 由授權服務判斷是否可對目標資源執行 |

初期角色定義與權限映射可集中在程式碼的一個 registry, 不必現在做自訂角色資料表或設定介面。成員紀錄保存 roleId, 避免把一整份權限複製到每個帳號, 以免定義修改後產生不同版本

Membership 保存 workspaceId、userId、roleId、status；ProjectMember 保存 projectId、userId、roleId, 並要求帳號仍是專案所屬空間的有效成員。角色定義包含 id、scope、label 與 permissionIds。跨空間角色或無效角色一律不產生授權

#### 操作只呼叫統一入口

以下是契約示意, 尚未實作：

```js
authorize(context, 'workspace.members.invite', workspaceResource);
authorize(context, 'project.read', projectResource);
authorize(context, 'issue.update', issueResource);
authorize(context, 'timeEntry.updateOwn', timeEntryResource);
```

context 的使用者來自已驗證 session, 角色與有效成員資格由後端當次讀取。resource 由後端以 ID 查回, 解析真實的 projectId／workspaceId／作者；不信任前端送入的 permissionIds、角色、作者或空間歸屬

畫面可用同一政策推導的 can／capabilities 決定按鈕是否呈現, 每次真正 API 操作仍重新授權。session 不保存可長期獨立生效的權限快照, 第一版不加入跨請求授權快取, 避免降權或移除後舊權限繼續可用

#### 適用範圍與規則是明確的

| 權限例子 | 賦予來源提案 | 執行時額外條件 |
| --- | --- | --- |
| workspace.members.invite | 提案為 Workspace owner／manager, 待細項確認 | 只對該空間, 能授予的角色另定, 不能任意升權 |
| project.readAny | Workspace owner／manager | 該空間所有專案讀取, 不需 Project 成員資格 |
| issue.updateAny | Workspace owner／manager | 權限 ID 提案：可修改該空間任一專案的 Issue, 仍須驗證 revision 與業務狀態, 不能跨空間 |
| project.read | 候選的負責人／PM／開發者／讀者, 待矩陣確認 | 只對有專案角色的那個專案 |
| issue.update | 候選為 PM／開發者, 負責人細項待定 | Issue 屬於該專案, 且專案可讀, 保存時仍驗證 Issue revision |
| timeEntry.updateOwn | 候選為 PM／開發者, 負責人細項待定 | 所屬專案可讀, 且 entry.userId 必須是操作者, 非作廢紀錄 |
| savedView.updateOwn | 另定對應操作角色 | 所屬專案可讀, 且作者為操作者；團隊分享不授予修改權 |

owner／manager 可操作全專案的方向已確認, 應展開成明確的全專案操作權限, 不只給 project.readAny。上表 permission ID 是契約提案；完整操作目錄與資料作者例外待細定, 不使用角色名稱全域放行或通用星號

user 不由 Workspace 成員資格直接取得任何專案讀取或寫入權。先檢查已加入目標 Project, 再展開對應專案角色的權限；加入了但沒有某個操作權限時仍拒絕該操作

#### 統一判斷順序

1. 驗證登入, 從可信資料解析目標資源的 Workspace 與專案
2. 檢查空間一致及成員仍有效, 失敗就拒絕, 任何角色都不能跨過這個邊界
3. 按目標範圍展開 Workspace 角色與該 Project 角色的有效權限；未知 permission ID／role ID 預設拒絕
4. 讀取專案時, 只接受 project.readAny（同空間）或有效 Project 成員資格＋project.read（該專案）, 不加入空間內可見途徑
5. 執行其他操作時, 檢查所需的全專案或單專案操作權限, 再檢查作者／狀態等該操作的資源條件。空間級全專案授予不要求逐一加入 Project, 單專案授予則要求有效 Project 成員資格；按授權來源判斷, 不寫 if role === user 的分支
6. 寫入在同一交易內重讀授權與 revision, 再進行異動, 確保授權檢查和資料寫入一致

已完成項目的重試也先重新授權, 才能讀取 requestId 對應結果。成員被移除或失去專案權限後, 不可用舊 requestId 讀回私人資料。列表／統計與單筆 API 共用政策判斷, 不只在詳細內容擋權限

第一版採範圍內的權限授予, 沒有每人 deny 例外或通用星號權限；空間／作者條件不能被一般 grant 略過。owner／manager 的全專案操作來源是明確列舉的範圍權限, 不使用角色名稱一律通過的全域捷徑

角色指派與 manager 提升須使用獨立管理政策及可授予角色名單；擁有權移轉也須獨立驗證, 不能因某人能邀請或修改普通成員就取得升權能力。正式可授予角色矩陣仍待確認

#### 現有程式的實際差距與遷移順序

本輪盤點發現目前原型仍有直接角色判斷：server/auth.js 的 invite, server/app.js 的 SMTP verify, src/domain/service.js 的狀態設定與通知可見性。視圖與工時另有作者檢查, getWorkspace 尚未按專案 ACL 過濾。這些不能因文件寫了 authorize 就算已完成

建議在實作專案 ACL 前一次整理以下範圍：

1. 先確認權限目錄與固定角色矩陣, 特別是 owner／manager 的全專案操作目錄、誰能建專案與授權角色
2. 建立集中 policy／authorize 與資源解析, 先以矩陣測試驗證, 呼叫端只依 permission ID 授權
3. 在同一個功能階段接齊 API 與列表／統計／通知／重試結果, 移除散落的 role === admin 判斷, 保留作者限制與業務狀態規則
4. 明確遷移舊 admin／member 與既有共享專案, 不把成員靜默升權, 也不突然改成私人造成資料無法存取

SMTP 目前是整個本機服務的設定, 遷移時須區分部署級 SMTP 管理與 Workspace 邀請權, 不讓新權限映射把空間管理者直接變成整個部署的管理者。SaaS 與自建共用同一組 policy 契約, 供應商／部署能力由 adapter 或明確能力設定補充

#### 實作前要通過的驗收情境

- 同樣顯示名稱但不同 roleId, 只按各自權限生效；改名／翻譯不影響授權
- 不同角色名稱但相同有效權限、scope 與資源條件, 授權結果一致；預設 manager 若未獲某操作權限, 不能因名稱補放行
- 同一人管理 A 空間, 無法讀取 B 空間, 也不能用 B 空間 ID 或其他專案角色混入權限
- owner／manager 不加入個別 Project 也能讀取與操作所屬空間全部專案, 操作來源為角色映射出的對應範圍權限
- user 未被加入 Project 時看不到專案且無法操作；加入後只有讀取權則仍不能寫, 取得開發者等角色的對應權限才可修改
- 開發者預設只能修改自己的有效工時；owner／manager 是否可代改他人須按完整操作矩陣測試, 不能只用全專案讀取權繞過作者條件
- 降權／退出空間後, 下一次 API 與舊 requestId 重試都不能繼續取得已失權資料
- 搜尋、統計、通知與共享視圖不能洩漏不可讀專案內容；未知權限／角色與無效資源預設拒絕

依據與界線：以上為 TaskTracker 的具體提案, 採納的是方向, 目前尚未改程式。[NIST RBAC](https://csrc.nist.gov/projects/role-based-access-control) 提供使用者、角色與權限分離的模型；[OWASP 授權指引](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) 建議預設拒絕、每次請求驗證授權, 並依資源屬性／關係補充判斷。因此此處採角色提供權限＋空間／專案／作者條件, 單純檢查有無某個權限字串仍不足以完成資源授權

3. 受邀者開啟邀請連結：沒有帳號就完成註冊與信箱驗證, 已有帳號就登入對應身分
4. 接受邀請後建立成員資格, 才取得該空間權限
5. 登入後可以選擇／切換自己加入的工作空間

信箱允許名單、公司網域限制可以是後續的加入政策, 單純填入 Email 不代表已驗證持有者, 也不應直接開放企業資料。是否支援這些政策、是否強制 SSO 尚未決定

## SaaS 與自建版本

使用者指出：「這樣切的話 SaaS 版本跟自建版本應該也會好切」

助理判斷 Workspace → Project → Issue 與空間內成員資格有利共用核心模型。建議維持同一套程式與資料結構, 以部署設定與 adapter 處理差異, 減少長期維護兩套業務規則的成本

| 項目 | SaaS 部署提案 | 自建部署提案 |
| --- | --- | --- |
| 核心功能 | Workspace、專案、Issue、工時與成員權限 | 沿用相同功能與授權規則 |
| 註冊／加入政策 | 可開放註冊並建立／加入空間 | 可設定僅邀請或由部署管理者初始化, 預設尚未定 |
| 空間數量 | 同一服務容納多個獨立工作空間 | 可以先用一個空間, 仍保留空間 ID 與隔離, 不移除資料層級 |
| 郵件／登入／儲存 | 由服務營運者設定供應商及部署資源 | 由自建維運者提供環境設定與必要服務 |
| 方案／帳務 | 需要時加在服務營運層 | 是否提供授權／額度限制另定, 不讓核心 Issue 操作依賴雲端帳單 |
| 升級與備份 | 服務營運者維護 | 自建維運者負責, 需提供版本遷移與備份／復原說明 |

建議把「整個部署的管理者」與「某個 Workspace 的管理者」分開定義。管理自己的空間不等於能管理其他客戶資料或部署設定；正式角色與後台權限尚未決定

容易分開部署不代表只要一個版本開關就完成交付, 後續仍須驗證設定、資料遷移、升級與外部服務依賴。目前 Compose 是本機開發設定, 尚未提供正式自建版安裝／升級套件；GAS 產檔仍依原約定暫緩, 兩版本方向未自動取代原先 GAS 評估

本節除了 D-009 的設計目標外, 都是實作與交付建議, 尚待確認

## 最新技術選型：Vue＋Vuetify／Laravel 前後端分離

2026-10-19 使用者指定 frontend 與 backend 兩個原始碼目錄, 根目錄保留專案 README, 並詢問是否改採 Inertia。依明確的前後端分離目標, 本輪採 Vue＋Vuetify 獨立 SPA 與 Laravel JSON API, 不使用 Inertia。Inertia 由伺服器頁面路由與 adapter 協調頁面, 更適合統一管理的 Laravel 應用；此處選分離式 API 是為了獨立開發、建置及部署, 不是宣稱 Inertia 無法提供其他 API

根目錄繼續保留 Compose、docs、plans 與 AGENTS, 「兩個資料夾」指產品原始碼的 frontend／backend。現有畫面與核心功能遷移, 不因整理目錄就清空資料或刪除歷史文件。Laravel 改為目前主後端, 舊 Node／GAS 架構與選型比較保留作沿革, 不要求同時維護三個執行環境

前端只依 HTTP API 存取資料；同一個對外 origin 反向代理 API 可減少 Cookie／CSRF 設定複雜度, 不妨礙原始碼與部署分離。正式若跨子網域部署須明確設定可信來源、Cookie 與憑證, 不用開放所有來源作捷徑。資料庫 schema 與 Project ACL 的完整重構另按前述契約推進, 本輪先確保功能相容、真正由 PHP 執行並可驗證

來源（查閱 2026-10-19）：[Laravel API 後端](https://laravel.com/docs/installation)、[Sanctum SPA 認證](https://laravel.com/docs/sanctum)、[Vuetify 安裝](https://vuetifyjs.com/en/getting-started/installation/)、[Inertia](https://inertiajs.com/)

### 已足夠開始, 但須分清原型與目標

Workspace → Project → Issue、帳號與成員資格分離、角色提供權限組合、以有效權限及 scope／資源條件授權, 已足夠作為下一版核心骨架。Epic、狀態分類、工時與依賴也已有試作及驗收規則, 不必等所有企業功能定案才開工

現有程式仍是 Node 原生 HTTP＋SQLite, Workspace 內共享專案, 沒有新 Project ACL。server/repository.js 使用 records(kind, id, payload) 存 JSON, 並非每個業務實體各有資料表；目前未提供完整業務外鍵、查詢索引與版本化 schema migration。這是本機試作取捨, 不代表 Node 或 SQLite 不能支援關聯模型, 換 Laravel 也不會自動完成權限或租戶隔離

### 下一版實作前先收斂三份契約

| 契約 | 最少需要定義 | 為什麼現在要處理 |
| --- | --- | --- |
| 權限目錄與預設矩陣 | 四組 Project 候選角色各有什麼權限；誰可建立／封存／刪除專案、指派角色、查看團隊工時與匯出；負責人與 PM 的差別；哪些作者限制需獨立授權 | authorize 的方向已定, 實際允許／拒絕必須有可測的依據, 不能在 API 各自猜 |
| 成員生命週期 | 新／舊帳號接受邀請、邀請過期／撤銷／重複接受、成員移除／降權、Project 除名、最後一位 Workspace owner 的保護；若採多空間則補選擇／切換 | 帳號登入與當前空間資格應分開, 不能把目前「登入挑第一個空間」當成長期契約 |
| 資料與遷移 | Workspace／Project membership、role／permission 映射、關聯及唯一性、revision／requestId 邊界、舊 admin／member 與共享專案怎麼轉換 | 先明確資料歸屬與遷移, 避免靜默升權、孤兒資料或升級後無人能管理；保留既有 Issue／工時與作者歷史 |

技術選型也應在大規模擴充後端前收斂, 但以上契約與驗收情境可沿用於 Laravel 或 Node。不要求先實作自訂角色、完整 workflow engine、SSO、群組或收費

### 還需要落實的工程工作

- **資料可見性是一整條查詢路徑**：專案列表、Issue 詳情、搜尋／統計、工時月曆、通知、團隊視圖與 requestId 重試結果都要套同一授權政策；前端只接收可讀資料, 不能下載整個 Workspace 後再隱藏卡片
- **撤權與多人同時修改**：下一次請求重查有效資格, 寫入與授權／revision 檢查維持一致；依據現有衝突處理延伸, 不把前端快取角色當成授權來源
- **查詢與資料結構**：以明確 membership、索引與分頁支援 100 個專案, 先建立可量測的查詢, 不急著拆微服務。若選關聯式 schema, SQLite 也可先做；正式資料庫採 MySQL 或 PostgreSQL 需另定, 不因換語言就宣稱已遷移
- **帳號與郵件**：公開部署前補信箱驗證、密碼復原、HTTPS／session／CSRF 與限流的正式設定。SMTP 真實寄送需背景工作、可重試與去重；保存業務事件與 outbox 後由 worker 處理, 與目前 preview／verify 區分
- **交付與維運**：面試可先有可重現的本機安裝與 CI, 正式 SaaS／自建交付再補 production image、migration、備份／還原演練、錯誤紀錄及健康檢查。現在的 Compose 是開發設定

上面是實作／上線階段的分工, 不是要求一次做完才可以試用。建議先完成完整的權限與成員流程, 再補實際寄信與部署；計費、SSO、即時推播及甘特圖可留後續

### Laravel 與 Node 的比較基準

Node.js 是 JavaScript runtime, Laravel 是 PHP web framework, 兩者層級不同。較公平的比較是 Laravel 與「Node＋選定的框架／套件／工程規範」；目前原生 HTTP 試作不等於已具備完整應用框架

| 方向 | 對本專案的好處 | 成本與界線 |
| --- | --- | --- |
| Laravel＋保留 Vue 前端 | 使用者已有長期經驗, 可把時間放在 SaaS 資料模型、權限、測試與完整流程；既有 Policies／Gates、SPA session 認證、Queue、Migration 可作基礎 | 需重寫目前 Node 後端與 JS domain 規則, 新建 PHP 測試並遷移資料；不能宣稱 JS domain 可直接在 PHP 重用。前端畫面與資料契約可盡量保留, 登入／CSRF 與錯誤處理需調整 adapter |
| 延續 Node, 整理為有明確模組的應用 | 可延用 JS domain、現有測試及 API, 若目標職缺要求 Node／TypeScript, 能直接展示該能力 | 仍需決定框架／驗證／資料遷移／背景工作與認證的整合, 補集中授權及資料層；可評估 NestJS 等方案, 不代表一定要換成某個框架或現在導入 TypeScript |

**助理建議／待確認：若主要目標是近期做出完整、能深入解說的面試作品, 優先考慮使用者熟悉的 Laravel＋現有 Vue, 採單體應用內清楚分模組。若主要目標是轉向 Node／TypeScript 職缺, 延續 Node 更符合展示目的**

這是依使用者經驗與作品目的作的判斷, 沒有調研目標公司職缺, 不宣稱哪個技術在市場上比較受歡迎。不必為展示技術同時維護兩套正式後端；Queue 初期可評估資料庫 driver, 不強制為履歷加入 Redis、微服務或 Kubernetes

不需把 framework 當成身份認同, 但 framework 的慣例、維護成本與團隊交接仍有實際價值。即使有 AI 協助生成程式, 面試仍應能說明自己的資料邊界、授權、交易、失敗處理與驗證, 並且能修改及除錯

### GAS 舊方向需要再作一次取捨

原架構保留 GAS 正式執行環境的方向, 現在加入 Laravel／Node 的面試選型, 必須確認主要交付目標。建議若以一般 SaaS／自建面試作品為主, 優先選一套常駐後端＋關聯式資料庫, GAS 留作之後另評估的部署或整合選項, 不同步開發三套。這是新建議, 尚未取代 D-003 與既有 GAS 約定

GAS 有執行時間、並行與服務配額, 背景寄信及多租戶查詢必須另作容量與一致性驗證, 不是套上 adapter 就能假定等價。採 Laravel 時, 若仍要求 GAS 後端, PHP／JS 業務邏輯會有額外的雙份維護成本

### 建議的實作順序與面試展示

1. **規格與選型階段**：確認預設權限矩陣、成員流程、主後端／資料庫與遷移策略, 產出可驗收的例子
2. **權限與協作階段**：完整接上 membership、集中授權與列表過濾, 提供專案成員管理, 驗證撤權、跨租戶拒絕與舊資料遷移
3. **可交付階段**：在既有 Issue／Epic／工時流程上驗證整合, 補背景通知、CI 與可重現部署；每階段各建立本機 commit

展示流程可以是：owner 建 Workspace／Project → 邀請 user, user 尚看不到任何專案 → 加入指定 Project 並授開發權限後才可開 Issue／填自己的工時 → 另一位只讀成員只能查獲授權的進度 → 兩人同時修改觸發 revision 衝突 → 移除成員後 API 與統計都不再回傳該專案。這些是待實作驗收, 不是目前功能已全數通過

面試的技術深度來自能解釋為什麼這樣切、怎麼證明沒有越權、失敗時如何恢復, 再以實際測試／部署證據支持。效能只報告量測的資料量與環境, 不預先宣稱高併發或大型 SaaS 已驗證

### 官方資料與判斷界線

查閱日期：2026-10-19, 下列是技術能力的依據, 選型結論與實作順序是助理建議

- [Laravel Authorization](https://laravel.com/docs/authorization)：Gates／Policies 提供授權組織方式, 仍須實作本專案的有效權限及 scope, 不採文件示例的管理員全域放行作捷徑
- [Laravel Sanctum](https://laravel.com/docs/sanctum)：第一方 SPA 可用 session cookie 與 CSRF 保護, 不因此自動完成信箱驗證、邀請與多租戶政策
- [Laravel Queues](https://laravel.com/docs/queues)：支援背景工作、失敗／重試及 transaction commit 後派送；afterCommit 本身不等同業務資料與 outbox 原子保存, 可靠性仍需設計
- [Laravel Migrations](https://laravel.com/docs/migrations)：提供資料庫 schema 變更管理, 資料遷移與還原程序仍需實作驗證
- [Node.js 簡介](https://nodejs.org/en/learn/getting-started/introduction-to-nodejs)與 [NestJS 文件](https://docs.nestjs.com/)：區分 runtime 與應用框架, 不把原生 HTTP 當成 Node 的唯一做法
- [GAS 配額](https://developers.google.com/apps-script/guides/services/quotas)：有服務及執行限制, 實際配額與帳號類型依部署時官方文件確認
