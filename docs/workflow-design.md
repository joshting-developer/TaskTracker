## 任務依賴

Epic 回答「這件事屬於哪個目標」, 前置任務回答「先完成什麼才能完成這件事」, 兩者分開保存

例如：付款 API → 付款介面 → 付款驗收。介面的 `blockedBy` 保存 API 的 ID, 驗收保存介面的 ID。詳細內容可以查看前置, API 詳細內容也會顯示哪些任務正在等待它

- 前置限同專案的 Task／Bug／Feature, 最多 20 個, 不接受自我、重複、Epic 或循環依賴
- 在同一 SQLite transaction 重新檢查整張依賴圖, 兩人反向建立依賴時, 後一筆不能形成循環
- 前置必須分類為 done 才代表交付。取消仍會阻擋, 要明確解除或替換前置
- 有未完成前置時不能轉完成；已完成的下游被重開的前置影響時, 保留狀態並標示「依賴需確認」, 不擅自級聯改狀態
- 已完成項目不能加上未完成的前置, 未完成項目則可以邊執行邊調整依賴
- 其他任務仍依賴這個執行項目時, 不能直接改成 Epic, 要先轉移依賴
- 關係異動記錄在 Issue history, 版本與 requestId 沿用既有機制；反向關係由來源推導, 不保存兩份連結
- 舊資料沒有 blockedBy 視為空陣列, 不批次重寫既有資料

任務清單與看板直接顯示所屬 Epic、實際／預估工時及阻擋標示。點 Epic 進父項目, 點阻擋提示進前置任務, 詳細內容顯示雙向依賴。跳轉前有未保存內容時提示捨棄確認

只對直接前置檢查交付, 不把間接祖先自動擴散成所有下游的阻擋。工作流狀態分類改變會重新影響提示, 狀態設定的驗收規則仍依協作設計

## 常用視圖

將目前專案的搜尋、狀態、優先級、成員、Epic、類型、特殊條件與排序保存。日常可以快速切「我的未完成 Bug」「待測試」「被阻擋」「逾期」, 不用反覆設定

視圖只保存查詢條件, 不複製 Issue／工時, 結果永遠根據最新資料。預設個人使用, 可明確選擇分享給目前工作空間的專案成員

- 個人視圖只有作者可讀；團隊視圖成員可讀, 只有作者可修改／刪除
- 每個視圖綁專案與作者, 查詢、異動和 requestId 都在工作空間內隔離
- 保存 ID 與固定欄位, 不接受可執行查詢或任意 SQL；多條件採 AND
- 刪除採封存, 重試不產生第二次操作, 不能透過 requestId 讀取其他人的私有視圖
- 重新整理保留選用的視圖, 網址可分享團隊視圖；無權讀取或無效連結不顯示私人名稱／查詢
- 參照的狀態／成員／Epic 不存在時提示修正, 不靜默放寬篩選

不增加跨專案任務首頁, 所有入口仍位於使用者選擇的專案中；不產生 GAS 或啟用真實寄信

使用方式：在專案清單／看板設定篩選 →「存為視圖」→ 填名稱、選只有我／團隊共用 → 儲存。上方按鈕可套用, 作者可用目前條件更新或移除。使用者調整條件後顯示「篩選已調整」, 不默默覆寫原視圖；背景載入新版時可按「重新套用」取得新版條件

視圖網址為 `#/projects/<id>?view=<viewId>`, 任務詳細內容保留 `?view` 以便關閉後回到同一視圖。非作者開私人連結時回到該專案, 只提示找不到可使用的視圖；分享「我的任務」依目前登入使用者計算, 不固化建立者 ID

篩選情況區分「被阻擋」（未結案＋未完成前置）與「依賴需確認」（完成＋前置重開）, 「逾期」只含未結案且到期日早於今天, 取消不列為逾期。多條件與文字搜尋一起採 AND, 我的任務範圍也與其他條件相交
