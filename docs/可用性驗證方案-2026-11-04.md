## 這與 UI／UX 的關係

你描述的是 UX 裡的可用性問題：使用者能否理解產品、找到動作、完成目標, 以及出錯後能否回來。它會受版面影響, 也會受名稱、資料順序、權限、入口與系統回饋影響。

前輪 Pro Max／Taste 已檢查文字、鍵盤、布局與部分操作, 有實際瀏覽器證據；但程式成功執行, 不代表第一次用的人知道該去哪裡。可用性測試則讓目標使用者完成具體工作, 觀察他的行為與理解。[NN/g 的方法介紹](https://www.nngroup.com/articles/usability-testing-101/)

## 建議先走這些任務

先挑一組角色、每次 3–4 個任務。不要把角色名稱混成權限判斷；測試環境依有效 permissions 安排。

| 任務 | 給參與者的目標, 不指示按鈕路徑 | 觀察者的完成條件與問題 |
| --- | --- | --- |
| T1 找到專案中的工作 | 你加入了團隊, 想找 first 裡交給你的工作, 看懂其中一件接下來要做什麼 | 有權看 first；是否先理解空間／專案；能否進到正確任務、找到描述與目前狀態 |
| T2 速記與交辦 | 剛聊完幾件小事, 先記下一件給自己, 再把另一件交給指定同事 | 是否找得到小待辦；理解這與正式任務的區別；交給正確的人, 知道已送出 |
| T3 把小事轉正式工作 | 昨天那件速記現在要團隊正式追蹤, 請安排進 first, 並補上需要的資訊 | 能否發現轉卡入口；選對 Project；知道原待辦是否保留, 避免重複建工作 |
| T4 辨識與更新進度 | 你想看 first 正在處理哪些工作, 並更新剛完成的一件 | 清單／看板怎麼選；是否理解狀態、Epic 分組；有沒有以為只移動畫面沒保存 |
| T5 記錄投入時間 | 將今天處理指定工作的半小時記下來, 再找出剛才的紀錄 | 日期入口、任務選擇與單位是否清楚；是否誤以為只能填指派自己的卡；能否確認保存 |
| T6 找回中斷的工作 | 你看到交辦通知, 想回去處理那件事；中途換過頁面, 請找回它 | 通知定位、預覽展開、返回／重整是否讓人迷路；不能只驗 API 仍有資料 |
| T7 讀者取得資訊 | 你只需要閱讀指定任務的要求與目前進度, 不負責修改 | 是否知道自己唯讀；能否找到描述／關聯；缺權限訊息是否被誤認為系統壞掉 |
| T8 管理者授權 | 讓指定同事參與 first, 並確認他能處理工作、不能看到 second | 分開空間成員與 Project 資格；角色權限說明是否理解；不假設加入 Workspace 即全部可見 |

表格第三欄只給觀察者, 不先念給參與者。新手題目使用情境語言, 不刻意塞進畫面標籤當答案；這種任務寫法符合 [NN/g 的任務情境建議](https://www.nngroup.com/articles/task-scenarios-usability-testing/)。

「畫面很雜」的評估也綁任務：他需要的資訊在哪裡？先被哪些東西吸引？是否為了找入口反覆捲動？隱藏資訊後是否反而找不到？不以元件數或頁面留白比例直接判好壞。首頁目前專案優先、待辦預覽三筆, 仍應同時觀察找專案及記小事兩個目標, 不把前輪修正當成最終答案。

## 建議採兩段驗證

**第一段：有限範圍的 AI 任務走查。** 指定角色、目標、起始頁、資料量與可接受終點；用隔離 Laravel／假帳號走正常、空資料、無權限、操作失敗及中斷後返回。先觀察介面提示, 再用程式確認成因；有程式內部資訊的發現另記, 不用已知網址或 selector 直接跳到入口後說「很好找」。目前不在這一輪執行。

**第二段：少量目標使用者的真人試跑。** 可先找沒有參與這個設計、但確實要協作的人, 每人挑 3–4 題, 主持人先不教路徑。先試跑一輪修正任務題目, 再規劃下一批受試者；這是本專案建議, 不保證某個固定人數可找到所有問題。同事若正是目標使用者可以參與, 熟悉度及便利樣本限制必須記下。

招募、聯絡、錄音／錄影與招募工具不由 skill 自動完成；本輪沒有向他人發送訊息。之後需要錄製時先讓參與者知道目的與保存方式, 也可以只做匿名筆記。

## 統一紀錄與問題排序

| 欄位 | 怎麼記 |
| --- | --- |
| 角色／經驗／環境 | 權限、是否熟悉產品、手機或桌面、起始頁與資料版本 |
| 結果 | 獨立完成／協助後完成／未完成；研究者沒跑到的要記未測, 不當成功 |
| 行為 | 實際路徑、第一個卡點、回頭／誤入、提示與復原；「不喜歡」和「完成不了」分開 |
| 數值 | 只記實際量測的時間、提示次數等；真人與 AI 不混算, 不編造停頓時間 |
| 佐證 | 畫面／步驟、實際原話或筆記, 匿名參與者代號；沒有原話不加引號假裝引用 |
| 解釋 | 與哪個任務相關、是入口難找、用語、資訊層級、權限還是回饋問題；推論標示推論 |
| 建議 | 能解決同一問題的最小修改、可能代價與重測任務；不直接採納所有使用者提的功能 |

問題先按「是否阻斷重要任務／是否容易做錯且難復原」排序, 再看完成成本與重複出現情況。少量參與者中單一嚴重事故仍值得優先處理；沒有樣本就不能寫「多數使用者」。不產一個缺乏依據的整體 UX 分數, 也不把 AI 模擬的信心當滿意度。
